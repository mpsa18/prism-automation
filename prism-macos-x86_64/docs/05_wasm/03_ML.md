# ML Inference: Integration Architecture

Status: the `prism:ml@0.1` ABI, the Rust SDK (`crates/ml-sdk`), the host
(`crates/ml-host`), the example plugin (Tract/ONNX,
`crates/ml-plugin-example`), the core runner
(`config/03_wasm/03_ml/<module>/`, `src/ml/`), batch reading and tag history are
ready. Feeding ML models into the control loop is out of scope: inference is
asynchronous by construction.

This document records the chosen architecture (requirement #5) and describes
operations: configuration, the Rhai API, metrics, model hot swap and fault
tolerance.

---

## 1. Decision: Tract inside Wasm (option B)

Of the two paths, **Tract (pure Rust, inside Wasm)** was chosen; WASI-NN is not
used and will not be mixed with it.

| Criterion | Tract inside Wasm (chosen) | WASI-NN |
|---|---|---|
| Isolation | Complete: an ML plugin has no host imports except `host.log` | Requires wasi-nn host imports and a native runtime (ONNX Runtime/OpenVINO) |
| API stability | The standard Wasmtime Component Model | `wasi-nn` in Wasmtime is experimental, the API is unstable |
| Deployment | A single `.wasm` artifact, nothing native | Native libraries for every OS/architecture |
| Performance | Sufficient for industrial telemetry (vectors of tens to hundreds of `f32`, periods 10 ms–1 s) | Closer to native, at the cost of isolation and operations |

Practical consequences:

- **The model remains a separate artifact.** The host reads the ONNX file and
  passes its bytes to `load-model(bytes, config)`; the plugin compiles the
  model with Tract inside the sandbox. This preserves model versioning and
  hot swap without rebuilding the plugin (requirement #4) and full isolation
  (requirement #9).
- A plugin may also carry an embedded model (`load-model(bytes: none)`) — the
  model version then equals the plugin version.
- Model compilation happens on the ML thread at load/replacement time, never
  in the control loop.

## 2. Data flow

```text
config/03_wasm/03_ml/<module>/*.toml
       │  [[plugin]] artifact + model + limits
       │  [[job]] schedule + features + outputs
       ▼
[TagRegistry] ──snapshot()/history()──► f32 feature vector
       ▲                                      │
       │                                      ▼
       │                        ml-host: wasmtime, sandbox,
       │                        fuel + memory + epoch watchdog
       │                                      │
       │   (job outputs)                      │ infer(features)
       └── write queue ◄──────────────────────┘
           TagWriter::Ml

Rhai (background poll threads): history(), snapshot(), ml_submit(),
ml_done(), ml_result(), ml_infer(), ml_metrics()
```

- **Batch reading.** `TagRegistry::snapshot(&[TagValue])` reads all tags in a
  single pass; a write-generation counter guarantees that no accepted write
  slipped between the reads (`coherent = true`), otherwise the snapshot is
  retried (up to 8 attempts) and only then returned best-effort.
- **Time windows.** Optional per-tag history is an in-memory ring buffer
  (`depth` samples, `sample_ms` decimation), configured in
  `config/01_southbound/06_history/history.toml`. Only real accepted samples are
  recorded (no force overrides and no rejected writes), with quality
  preserved.
- **Features.** A job assembles a vector from two kinds of items:
  `kind = "value"` (the current value) and `kind = "history"` (the last
  `max_samples` values within `window_ms`, padded with `first|zero|nan` when
  short, then `scale`/`offset`). Invalid values enter as `NaN`.

## 3. The `prism:ml@0.1` contract

Full WIT: `crates/ml-wit/wit/ml.wit`.

```wit
world ml-plugin {
  import host;                       // host.log only
  export ml;
}

interface ml {
  get-info: func() -> plugin-info;
  load-model: func(bytes: option<list<u8>>, config: option<string>)
      -> result<model-info, string>;
  infer: func(features: list<f32>) -> result<list<f32>, string>;
}
```

Key differences from `prism:compute` (`01_PLUGIN_SDK.md`):

- there is no tag `read`/`write` and no registry access at all — data arrives
  in **one call**, which rules out reentrancy and inconsistent reads;
- there are no blocks or schedules inside the plugin — the host owns the
  schedule;
- the model is a separate artifact, not just plugin code.

## 4. Asynchrony (requirement #6)

Inference is **never** called synchronously from the control loop:

- every job runs on the plugin's dedicated thread with its own period; outputs
  are written to tags through a queue (`TagWriter::Ml`), not from the control
  path;
- Rhai scripts use `ml_submit()` (non-blocking) and poll
  `ml_done()`/`ml_result()`; the synchronous `ml_infer()` is allowed only in
  background `[[poll]]` threads and **refuses** to run from the control path
  (virtual tags, alarm handlers) — see §6;
- the request queue is bounded (`queue_capacity`); overflow is counted as the
  `dropped` metric, not turned into blocking.

The typical pattern is for the host to invoke ML on a schedule and put the
result into a tag; Rhai reads the ready value:

```rhai
// [[poll]] function: assemble features, submit asynchronously, keep the id
fn submit_anomaly() {
    let vib = history("motor1/vib", 1000);
    if vib.len() >= 32 {
        let features = [];
        for i in 0..32 { features.push(vib[vib.len() - 32 + i]); }
        let id = ml_submit("anomaly", features);
        write("ml.pending_id", id);
    }
}

// another [[poll]] function: collect the finished result
fn collect_anomaly() {
    let id = read("ml.pending_id");
    if id >= 0 && ml_done(id) {
        let out = ml_result(id);
        if out.len() > 0 {
            write("ml.anomaly_score", out[0]);
            if out[0] > 0.8 { raise_alarm("ml.anomaly", "high anomaly score"); }
        }
    }
}
```

## 5. Model registry, hot swap, rollback (#4)

- The model is a file (`model = "../models/anomaly_v2.onnx"`); the version is
  `model_version` from the config or a content hash prefix; the version is
  visible in the metrics and the replay log.
- Hot swap: the worker watches the artifact and model mtime/size. Replacing
  the model file reloads it into the live instance (without recreating the
  component); replacing the `.wasm` builds a new instance while the previous
  one stays in memory.
- Rollback: after `auto_rollback_after` consecutive failures of the new
  artifact, the runner returns to the previous instance and records it with
  the `rollbacks` metric. A failed load (of either the model or the artifact)
  leaves the running version untouched.
- The compiled component is cached by (path, mtime+size): a restart after a
  crash and a rollback do not rebuild the heavy Tract artifact.

## 6. Rhai API (#7)

| Function | Purpose |
|---|---|
| `snapshot(["dev.a", "dev.b"])` | Coherent snapshot of values (`NaN` for unknown tags) |
| `snapshot_quality([...])` | Quality of the same tags (`"good"`, `"bad"`, ...) |
| `history("dev.tag", window_ms)` | Tag-history values within the window (oldest → newest) |
| `history_samples("dev.tag", window_ms)` | The same with `{value, ts_ms, mono_ms, quality}` |
| `ml_submit("plugin", features)` | Asynchronous request → job id (`-1` when rejected) |
| `ml_done(id)` | The job has finished (successfully or with an error) |
| `ml_result(id)` | Model outputs; an empty array while no result is ready |
| `ml_error(id)` | The job's error text (an empty string on success) |
| `ml_infer("plugin", features)` | Synchronous call; **forbidden** on the control path |
| `ml_metrics()` / `ml_metrics("plugin")` | Inference metrics per plugin |

## 7. Metrics and replay (#8)

Per plugin: `calls`, `errors`, `timeouts`, `traps`, `dropped`, `restarts`,
`rollbacks`, `consecutive_failures`, `last_latency_us`,
`latency_us_p50/p95/p99` (a sliding window of the last 512 calls), the last
output vector, the model version and the artifact hash. Access:

- Rhai: `ml_metrics()` / `ml_metrics("plugin")`;
- Prometheus: `/metrics` (the health server) — `prism_ml_calls_total`,
  `prism_ml_errors_total{kind=...}`, `prism_ml_restarts_total{kind=...}`,
  `prism_ml_latency_microseconds{quantile=...}`, `prism_ml_model_info`;
- the log: every call is a debug line, failures are warn/error; with replay
  enabled, a full journal with inputs and outputs.

The replay log (`[defaults].replay = true`, `replay_dir`, `replay_max_mb`) is
a JSONL file `inference.jsonl` (with `.1` rotation) whose lines are
`{ts_ms, plugin, job, source, artifact, model, latency_us, ok, error,
features, outputs}`. It lets a new model be replayed offline against the same
inputs; both successful and failed calls are recorded.

## 8. Isolation and resource limits (#9)

- The plugin has no access to the filesystem, the network, clocks or tags; its
  only side effect is `host.log`.
- `max_memory_mb` — the instance's linear-memory limit.
- `fuel_per_call` — the per-call CPU budget (deterministic).
- `timeout_ms` — the wall-clock watchdog (wasmtime epoch interruption): a hung
  model is interrupted, the instance is marked poisoned, and the runner
  rebuilds it with backoff (`restart_backoff_ms`, exponentially up to 60 s).
- The host distinguishes `InferError` kinds: `Timeout`, `OutOfFuel`, `Trap`,
  `Plugin`, `Contract`; all of them are metrics, never a platform crash.
- Interface bounds: the model's input/output sizes are validated
  (`input-size`/`output-size`, limits 65 536 / 4 096); a feature-vector
  mismatch is a rejected call, not a read of someone else's memory.

## 9. Configuration reference

`config/03_wasm/03_ml/<module>/*.toml` (fragments of one module are read in
name order; an instance may have several modules).

```toml
[defaults]
enabled = true
result_ttl_ms = 60000      # how long an on-demand result stays readable
adhoc_wait_ms = 2000       # upper bound of the synchronous ml_infer
replay = false
replay_dir = "../data/ml/replay"
replay_max_mb = 64

[[plugin]]
id = "anomaly"
path = "../plugins/anomaly/anomaly.wasm"
max_memory_mb = 128
fuel_per_call = 2000000000
timeout_ms = 500           # per-call watchdog; 0 — no limit (not recommended)
restart_backoff_ms = 5000
auto_rollback_after = 3    # 0 — no auto-rollback
model = "../models/anomaly_v2.onnx"   # omit the key for an embedded model
model_version = "2.0.0"    # defaults to a hash prefix
model_config = '{"normalize": true}'
queue_capacity = 64

[[job]]
name = "motor1_anomaly"
plugin = "anomaly"
period_ms = 100
error_policy = "log_and_hold"   # log_and_hold | backoff | disable

[[job.feature]]
tag = "motor1.vib"
kind = "history"           # value (default) | history
window_ms = 1000
max_samples = 128          # may be omitted when the model input size implies it
pad = "first"              # first | zero | nan
scale = 1.0
offset = 0.0

[[job.output]]
tag = "ml.motor1_score"    # the tag must exist (virtual/device)
index = 0
scale = 1.0
```

Tag history (`config/01_southbound/06_history/history.toml`):

```toml
[defaults]
depth = 1000        # samples per tag (~32 bytes/sample of memory)
sample_ms = 100     # decimation

[[tag]]
id = "motor1.vib"
depth = 2000
sample_ms = 20
```

## 10. Building plugins

```sh
# The regular release profile uses fat LTO and is impractical for Tract:
cargo build -p ml-plugin-example --target wasm32-wasip2 --profile wasm-plugin
# Artifact: target/wasm32-wasip2/wasm-plugin/ml_plugin_example.wasm
```

The `wasm-plugin` profile (root `Cargo.toml`) is the deployment compromise:
`lto = false`, `codegen-units = 16`, `debug = 0`; a debug build of a
Tract-based plugin weighs hundreds of MB and makes wasmtime compile it for
minutes.

An external developer does not need this profile: a project created by
`prism-devtools ml new` already carries its own `[profile.release]` with the
same settings (§11) and builds with a plain `cargo build --release`.

The example plugin also carries a stand for acceptance drills — the
`load-model` config `{"simulate": {"hang_ms": 5000, "trap": true,
"error": "..."}}` verifies that a hung or crashed model never takes the
platform down.

## 11. For an external developer: the workflow

An external developer receives **only the binary, configs, tooling and
documentation** — the core sources are not needed to build a plugin. The
contract is closed by three things:

1. **The contract ships as an artifact.** `prism-devtools ml new` puts a copy
   of `ml.wit` right into the plugin project (`wit/ml.wit`); the host compares
   the ABI version exactly and rejects a mismatch, so a divergence is caught
   at load time, not at runtime.
2. **No SDK is required.** The WIT world can be implemented in any language
   with Component Model support (`wit-bindgen`: Rust, C, Go, Python…); for
   Rust the scaffolder generates a project that needs only `wit-bindgen` from
   crates.io. There is no `prism-sdk` — the contract is the SDK.
3. **Installation is files.** The artifact is copied into `plugins/`, the
   module config into `config/03_wasm/03_ml/<module>/`; the platform picks up a
   replaced `.wasm` or model by itself (hot swap), no restart needed.

### Step by step

```sh
# 1. Scaffold: plugin project + module config template
#    (--root is the instance directory, next to prism)
devtools/tooling/prism-devtools ml new anomaly

# 2. Model and code:
#    plugins/ml/anomaly/models/anomaly_v1.onnx     — the ONNX artifact
#    plugins/ml/anomaly/src/lib.rs                 — get-info/load-model/infer
#    plugins/ml/anomaly/Cargo.toml                 — uncomment tract-onnx

# 3. Build (only Rust and targets are needed):
rustup target add wasm32-wasip2
cd plugins/ml/anomaly
cargo build --release --target wasm32-wasip2

# 4. Install:
cp target/wasm32-wasip2/release/ml_plugin_anomaly.wasm anomaly.wasm
#    then uncomment [[plugin]]/[[job]] in
#    config/03_wasm/03_ml/anomaly/anomaly.toml and set the tags;
#    press 'r' in the prism console to reread the config
```

### What an integrator should know

- **Asynchrony is part of the contract**: `infer` is invoked by the host on a
  dedicated thread (on the `[[job]]` schedule or via `ml_submit` from Rhai) —
  the real-time control loop needs no special care; blocking calls on the
  control path do not exist by construction.
- **Features and windows**: `[[job.feature]]` supports the current value and a
  history window (`kind = "history"`); history is enabled per tag in
  `config/01_southbound/06_history/history.toml`. The host validates the vector
  size against the model `input-size`.
- **Reliability**: a hang is interrupted by the watchdog (`timeout_ms`), a
  panic becomes a trap; the runner rebuilds the instance and, after a series
  of failures of a new version, rolls back to the previous one. The platform
  keeps running in every case.
- **Model versioning**: files `*_v1.onnx`, `*_v2.onnx` plus the
  `model`/`model_version` keys; replacing the file is a hot switch; the
  current version and its metrics are visible in `ml_metrics()` and
  `/metrics`.
- **Debugging without core sources**: `ml_metrics("anomaly")` from Rhai,
  `/metrics` (Prometheus), `[defaults].replay = true` — a JSONL journal with
  every input/output/latency for offline replay of a new model.
- **Platform upgrades**: when the ABI changes, the host rejects the old copy
  of `wit/ml.wit` with an explicit error; update the copy and rebuild the
  plugin.

### Acceptance checklist for an external plugin

1. The plugin loads on an instance without core sources (`ml new` → build →
   files).
2. A vector of 100+ features is accepted by a single `infer` without a
   timeout.
3. Replacing the ONNX file changes the output without a restart (hot swap).
4. A hung (or panicking) model does not disturb the rest of the platform:
   `timeouts`/`traps` in the metrics, the plugin recovers by itself.
5. Latency is visible in the metrics/replay; model outputs land in tags and
   are available to Rhai/MQTT/OPC UA like any other values.

## 12. Readiness criteria

1. **100+ features in one call** — `[[job.feature]]`/`max_samples` are
   assembled into a single `list<f32>`; sizes are validated on the host and
   in the plugin.
2. **Inference does not block the control loop** — ML threads plus a queue;
   the control path refuses `ml_infer`.
3. **Model replacement without a restart** — hot swap of the model/artifact
   file, the version in the metrics, auto-rollback and a compile cache.
4. **Isolation** — a WIT world with no imports except `host.log`; memory,
   fuel and wall-clock limits.
5. **Rhai orchestrates the pipeline** — `history`/`snapshot`/`ml_submit`/
   `ml_result`/`ml_metrics` (see §6).
6. **Latency is measured and logged** — p50/p95/p99, `last_latency_us`, the
   replay log.
7. **The platform survives an ML crash or hang** — the watchdog, poisoning →
   rebuild with backoff, rollback; an inference failure never goes beyond the
   metrics and logs.
